# Design Experiments

The simulator exists to answer one question before any hardware is built:
**which cache design should I use for this workload?** These five experiments
show how to answer it. Each one changes a single design parameter and keeps
everything else fixed.

All numbers come from `tools/run_experiments.py`. The raw CSV files are in
[`results/`](results/). The workloads are in `traces/workloads/` and are
generated by `tools/gen_traces.py`; every file starts with a comment that
describes it.

Unless stated otherwise: 64-byte blocks, LRU, write-back + write-allocate,
1-cycle hit, 100-cycle miss penalty.

---

## 1. How many ways do I need?

32 KiB cache, associativity varied.

| Workload | 1-way | 2-way | 4-way | 8-way | 16-way |
|---|---:|---:|---:|---:|---:|
| `conflict_stride` (8 blocks, same set) | 0.0% | 0.0% | 0.0% | **99.9%** | 99.9% |
| `memcpy` (src and dst in same set) | 0.0% | **93.8%** | 93.8% | 93.8% | 93.8% |

**What happens.** In `conflict_stride`, 8 addresses are exactly 32 KiB apart,
so they all have the same set index. With fewer than 8 ways, each new block
evicts one that is needed soon, and nothing ever hits. With 8 ways, all of
them fit. In `memcpy`, `src[i]` and `dst[i]` collide, so 2 ways are enough.

**Decision.** Choose the number of ways from how many hot blocks collide in
one set. Ways beyond that cost comparators and power and buy nothing: 16-way
is no better than 8-way here, and 4-way is no better than 2-way for memcpy.

---

## 2. How big should the cache be?

4-way, size varied.

| Workload | 4 KiB | 8 KiB | 16 KiB | 32 KiB | 64 KiB |
|---|---:|---:|---:|---:|---:|
| `hot_cold` (16 KiB hot data) | 19.9% | 39.5% | 75.0% | **88.6%** | 89.1% |
| `cyclic_36k` (36 KiB loop) | 93.8% | 93.8% | 93.8% | 95.8% | **98.4%** |

**What happens.** In `hot_cold`, the hit rate rises steeply until the cache
holds the 16 KiB hot region, plus some room for the cold traffic passing
through. After 32 KiB it flattens: 64 KiB doubles the area for +0.5%.

`cyclic_36k` is the opposite. A loop over 36 KiB gets *no* reuse from any
cache smaller than 36 KiB. The 93.8% at 4–16 KiB is pure spatial locality
(15 of every 16 accesses hit the block just loaded). Only when the whole loop
fits do we get reuse between passes.

**Decision.** Find the "knee" where the curve flattens: 32 KiB for
`hot_cold`. For loops, the cache must hold the whole loop. A cache slightly
too small is about as bad as a much smaller one.

## 3. Which replacement policy?

32 KiB, 8-way.

| Workload | LRU | FIFO | Random |
|---|---:|---:|---:|
| `hot_cold` | **88.9%** | 82.8% | 83.3% |
| `cyclic_36k` | 93.8% | 93.8% | **97.5%** |

**What happens.** In `hot_cold`, the hot blocks are used constantly, so
LRU almost never evicts them. FIFO evicts them anyway once they are the oldest
loaded, and Random sometimes picks them.

In `cyclic_36k`, the loop is a bit larger than the cache. LRU always evicts
the block that is used furthest in the past, which in a loop is exactly the
one needed next. LRU therefore gets no reuse at all. Random keeps a random
part of the loop and gets some.

**Decision.** There is no policy that always wins. LRU is the best default
for normal programs, which reuse recent data. But it has a known worst case
(loops slightly larger than the cache), and Random is cheaper in hardware and
has no worst case. This is why real CPUs often use pseudo-LRU, an
approximation of LRU with fewer bits, or mix in some randomness.

## 4. Write-back or write-through?

32 KiB, 2-way. Bytes moved between cache and memory. Dirty lines still in the
cache at the end are counted as written, because they would be on a flush.

| Workload | Policy | Read from memory | Written to memory |
|---|---|---:|---:|
| `histogram` | write-back | 8 KiB | **8 KiB** |
| `histogram` | write-through | 8 KiB | 80 KB |
| `memcpy` | write-allocate | 128 KiB | 64 KiB |
| `memcpy` | no-write-allocate | **32 KiB** | 64 KiB |

**What happens.** `histogram` writes the same 8 KiB table 20,000 times.
Write-back keeps those writes in the cache and writes each block out once.
Write-through sends all 20,000 stores to memory, which is **10× the traffic**.

`memcpy` writes each destination word once. Write-back saves nothing there,
since every block is written once either way. Write-allocate also *reads*
each destination block from memory only to overwrite it completely, which
gives 4× the read traffic of no-write-allocate.

**Decision.** Write-back is the right default when data is written
repeatedly, which is common (stack, counters, buffers). For streaming writes
that are never read back, no-write-allocate avoids useless fetches. This is
the idea behind the "non-temporal" store instructions in real CPUs. In
embedded systems, memory traffic means power, so this difference matters.

## 5. Can software fix what hardware can't?

128×128 `int` matrix (64 KiB), 32 KiB cache.

| Access pattern | 1-way | 2-way | 8-way | fully assoc. |
|---|---:|---:|---:|---:|
| row by row | 93.8% | 93.8% | 93.8% | 93.8% |
| column by column | 0.0% | 0.0% | 0.0% | 93.8% |
| column by column, rows padded to 129 | 91.7% | 93.0% | 93.0% | 93.0% |

**What happens.** Going down a column, each access is one row (512 bytes)
further. 512 is a power of two, so the 128 blocks of a column fall into very
few sets: 64 sets in direct-mapped, 32 in 2-way, 8 in 8-way. Each of those
sets receives more blocks than it has ways, so the column evicts itself.
Adding ways doesn't help, because more ways means fewer sets, so the blocks
still collide. Only a fully associative cache, which has no sets, avoids it.

Padding each row by one `int` (516 bytes) breaks the power-of-two stride.
The column then spreads over many sets, and even a direct-mapped cache gets
91.7%.

**Decision.** Some access patterns defeat any reasonable cache. Before you
spend hardware on them, check whether a small change in data layout fixes the
problem for free.

---

## Summary

| Question | Answer from the experiments |
|---|---|
| Ways | As many as the blocks that collide in one set; more is wasted. |
| Size | Just past the knee of the hit-rate curve; loops must fit completely. |
| Replacement | LRU by default; it has a worst case (loops slightly bigger than the cache). |
| Write policy | Write-back for repeated writes (10× less traffic); no-write-allocate for streaming. |
| Layout | Power-of-two strides can defeat any set-associative cache; padding fixes it. |

## Reproducing

```sh
python tools/gen_traces.py                # regenerate traces (already committed)
python tools/run_experiments.py           # rerun everything, writes docs/results/*.csv
```

Python is only needed for these two scripts. The simulator itself is plain C.
